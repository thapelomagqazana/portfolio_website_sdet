## 1. Purpose

This document defines the content required for the portfolio website.

The portfolio is not intended to be a collection of decorative sections. Every section must have a clear job in the visitor journey.

The core principle is:

> **Every section must either explain, prove, orient, build trust, or enable action.**

If a section does none of these things, it should not exist.

---

# 2. Content Strategy

## 2.1 Primary Audience

The primary audience is:

1. QA recruiters
2. QA hiring managers
3. Engineering managers

They should be able to answer three questions quickly:

### Question 1 — Who is Thapelo?

A QA Engineer / Software Tester moving toward Test Automation and Quality Engineering.

### Question 2 — Can Thapelo actually do the work?

The portfolio must provide evidence through:

- Professional experience
- Projects
- Test automation
- API testing
- CI/CD
- Software engineering
- Quality engineering practices
- Technical writing

### Question 3 — How can I contact him?

Contact and professional social links must always be easy to find.

# 14. C-10 — Engineering Philosophy

## Purpose

Show how Thapelo thinks about engineering.

This section differentiates the portfolio from a conventional CV website.

## Core Principles

### 01 — Understand

```text
Understand the system before testing the system.
```

Understand:

* Requirements
* Architecture
* User behaviour
* Data
* Dependencies
* Failure modes

---

### 02 — Challenge

```text
Do not only test what should happen.
Test what could go wrong.
```

Think about:

* Boundary conditions
* Invalid input
* Integration failures
* Unexpected state
* Security risks
* Performance limits
* Failure recovery

---

### 03 — Automate

```text
Automate repeatable work so humans can focus on thinking.
```

Automation should provide:

* Speed
* Repeatability
* Consistency
* Fast feedback
* Regression protection

Automation is not valuable simply because it is automated.

---

### 04 — Evidence

```text
A quality decision should be supported by evidence.
```

Evidence can include:

* Test results
* Defect reports
* Logs
* Coverage
* Security results
* Performance results
* CI/CD results
* Release gates

## Closing Principle

```text
Build. Test. Automate. Ship with confidence.
```

# 20. Content Quality Rules

All portfolio content must follow these rules.

## Rule 1 — Evidence Over Claims

Prefer:

```text
Created 100+ test scenarios.
```

over:

```text
Excellent tester with extensive experience.
```

Where appropriate, link claims to evidence.

---

## Rule 2 — Never Invent Metrics

Do not invent:

* Users
* Customers
* Revenue
* Performance improvements
* Defects
* Test counts
* Downloads
* GitHub stars
* Production deployments

If a number is unknown, omit it.

---

## Rule 3 — Separate Professional Work From Personal Work

Professional experience:

```text
Alula Technologies
C. Steinweg Bridge Ltd
```

Independent engineering:

```text
QINIS
BrikByteOS
```

Do not blur these categories.

---

## Rule 4 — Keep Content Scannable

Use:

* Short paragraphs
* Clear headings
* Bullets
* Evidence
* Technical labels
* Progressive disclosure

Avoid:

* Large walls of text
* Repeated information
* Generic motivational statements
* Excessive jargon

---

## Rule 5 — Content Must Be Maintainable

Project and experience information should eventually be stored as structured content rather than hard-coded repeatedly across components.

Example conceptual model:

```ts
type Experience = {
  company: string
  role: string
  period: string
  location?: string
  summary: string
  achievements: string[]
}
```

This allows content to evolve without redesigning the UI.

# 24. Section Purpose Test

Before adding any future section, ask:

### Question 1

```text
What user question does this section answer?
```

### Question 2

```text
What evidence does this section provide?
```

### Question 3

```text
Does another section already answer this question?
```

### Question 4

```text
Does this section move the visitor toward trust or action?
```

### Question 5

```text
What would be lost if we removed it?
```

If the answer to Question 5 is:

```text
Nothing meaningful.
```

The section should be removed.
